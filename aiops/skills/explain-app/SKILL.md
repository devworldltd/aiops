# /explain-app — 앱 구조 해설 문서 만들기

앱 하나가 **어떻게 동작하는지**를, 개발 지식이 없는 사람이 읽을 수 있게 그림으로 설명하는
HTML 문서를 만들고 Artifact 로 게시한다.

읽는 사람은 **동료·고객·경영진**이다. 개발자용 문서(`docs/ARCHITECTURE.md`·`docs/SERVICES.md`)와
목적이 다르다 — 여기서는 파일 경로·바인딩 이름이 아니라 **일의 흐름과 그렇게 만든 이유**를 말한다.

> 기준 사례: `reference/example.html`. 새로 만들 때 **먼저 이 파일을 읽어** 구조·톤·SVG
> 관용구를 확인한다. 처음부터 CSS 를 다시 짜지 않는다.

---

## STEP 0 — 대상 정하기

1. 인자로 앱 이름이 오면 그것(`/aiops:explain-app <앱>`).
2. 없으면 현재 브랜치에서 유추한다 — `feature/<app>/issue-N` 이면 2번째 세그먼트.
3. 그래도 모르면 **묻는다.** 후보는 레포에서 읽는다(하드코딩 금지 — 앱은 계속 늘어난다):

```bash
# base ref 와 후보 루트는 /aiops:focus 와 같은 규약을 쓴다(레포마다 다르다).
BASE=$(git config --get aiops.worktreeBase || true)
if [[ -z "$BASE" ]]; then
  git rev-parse --verify --quiet origin/dev >/dev/null && BASE=origin/dev \
    || BASE=$(git symbolic-ref --quiet refs/remotes/origin/HEAD | sed 's|refs/remotes/||')
fi
BASE=${BASE:-origin/main}
ROOTS=$(git config --get aiops.worktreeRoots || echo "apps services")
for r in $ROOTS; do git ls-tree --name-only "$BASE" "$r/" 2>/dev/null | sed "s|$r/||"; done | sort -u
```

`services/` 의 실행체도 대상이 될 수 있다(순수 Worker·브리지 등). 앱이 아니어도 절차는 같다.
후보 루트가 없는 **단일 레포**면 대상은 레포 자체다 — 아래 근거 수집에서 `apps/$APP/` 대신
레포 루트를 훑는다.

## STEP 1 — 근거 수집 (지어내지 않기 위한 단계)

**이 문서의 모든 숫자와 흐름은 아래에서 나와야 한다.** 기억이나 추측으로 쓰지 않는다.

```bash
APP=<앱>
ROOT=apps/$APP; [[ -d "$ROOT" ]] || ROOT=services/$APP; [[ -d "$ROOT" ]] || ROOT=.

# ① 서비스 레지스트리 — **있는 레포에서만.** 이 서비스가 무엇이라고 선언돼 있나(진실원천)
#    파일명은 레포마다 다르다. 없으면 ②③ 과 README 로 대체한다(억지로 찾지 말 것).
REG=$(ls registry/services.yaml services.yaml 2>/dev/null | head -1)
[[ -n "$REG" ]] && grep -A 20 "key: $APP" "$REG" || echo "(레지스트리 없음 — 배포 설정·README 로 대체)"

# ② 배포·바인딩·설정 — 주석이 대개 "왜" 를 담고 있다. 통째로 읽을 것
#    스택에 따라 파일이 다르다: wrangler.jsonc(CF Workers) · Dockerfile · fly.toml ·
#    vercel.json · pyproject.toml · package.json 중 **있는 것**을 읽는다.
ls "$ROOT" | head -30
cat "$ROOT"/wrangler.jsonc 2>/dev/null || cat "$ROOT"/Dockerfile 2>/dev/null

# ③ 데이터 모양과 그 이유 — 마이그레이션 주석이 설계 근거의 금광이다
cat "$ROOT"/migrations/*.sql 2>/dev/null || cat "$ROOT"/**/migrations/*.py 2>/dev/null

# ④ 핵심 로직의 머리 주석 — "왜" 를 파일 상단에 적는 레포에서 특히 값이 크다
head -40 "$ROOT"/lib/*.* 2>/dev/null

# ⑤ 라우트·엔드포인트 = 사용자가 할 수 있는 일 (프레임워크에 맞춰 찾는다)
find "$ROOT" -name "route.ts" -o -name "routes*.py" -o -name "*.controller.*" 2>/dev/null | head -20

# ⑥ 의존하는 백엔드가 있으면 그쪽 README (계약·실측 기록이 있다)
cat services/<backend>/README.md 2>/dev/null
```

수집하면서 아래를 채운다. 비어 있는 칸이 있으면 **그 항목은 문서에 쓰지 않는다**.

> 아래 "어디서" 는 **그 레포에서 같은 역할을 하는 파일**을 가리킨다. 파일명·필드명은 스택마다 다르다
> (배포 설정이 `wrangler.jsonc`·`Dockerfile`·`fly.toml` 중 무엇인지, 인증이 미들웨어인지 데코레이터인지).
> **없는 항목은 비워 두고 문서에 쓰지 않는다** — 억지로 찾아 맞추면 지어내게 된다.

| 항목 | 어디서 (역할로 읽을 것) |
|---|---|
| 한 줄 소개 · 도메인 · 상태 | 레지스트리(있으면)의 설명·도메인·상태 필드 |
| 누가 쓸 수 있나 | 레지스트리의 접근 등급 + 인증·인가 게이트 코드 |
| 무엇을 저장하나 | 배포 설정의 스토리지 바인딩(DB·오브젝트·KV) 또는 DB 접속 설정 |
| 비동기 여부 | 큐·워커·잡 스케줄러 바인딩 유무 + 진행 상태를 다루는 로직 |
| 바깥에 무엇을 부르나 | 환경변수의 `*_URL`·API 키 이름 + 레지스트리의 의존 서비스 |
| 자동 실행 | Cron·스케줄 트리거 설정 |
| 보관·파기 | 파기·정리 로직의 상수(보관 일수 등) |
| 실측·의사결정 기록 | 코드 주석의 경고 블록, 의존 서비스 README 의 비교표 |

## STEP 2 — 그림 고르기

**여정도 1개는 필수**, 여기에 그 앱에서 실제로 설명할 가치가 있는 메커니즘을 **2~4개** 더한다.
앱마다 다른 그림이 나와야 정상이다 — 같은 5개를 모든 앱에 복사하면 그 순간 템플릿이 된다.

레시피와 좌표 관용구는 **`reference/diagram-recipes.md`** 에 있다. 요약:

| 레시피 | 언제 쓰나 | 무엇을 주장하나 |
|---|---|---|
| **여정도** (필수) | 항상 | 일이 어느 지대에서 벌어지고 경계를 몇 번 넘는가 |
| 대기열 3단 | Queue 바인딩이 있을 때 | 요청과 처리가 분리돼 있고 결과가 되돌아오는 길 |
| 상태 흐름 | 오래 걸리고 재개되는 작업 | 중단돼도 이어지는 이유 |
| 방법 비교 | 두 방식을 합쳐 쓸 때 | 하나만 쓰면 각각 어떻게 다르게 틀리는가 |
| 관문 | 접근 제한이 있을 때 | 단계 순서에 이유가 있다는 것 |
| 순서 중요도 | 뒤집으면 깨지는 순서(파기·마이그레이션) | 왜 이 순서여야만 하는가 |
| 일정 타임라인 | Cron 이 여럿일 때 | 언제 무엇이 저절로 일어나는가 |

**고르는 기준**: 그림이 문장보다 빠르게 설명하는가. 아니면 문장으로 쓴다.
박스 3개에 이름만 적은 그림은 이미 있는 문장을 다시 쓴 것이다.

## STEP 3 — 원고 · 용어 규약

### 위치는 숨긴다 (강제)

서버가 **어디에 있는지 쓰지 않는다** — 사무실·자택·특정 도시·특정 국가·"우리 책상 위" 모두 금지.
대외 공개 가능성이 있는 문서라 그렇다.

연산 백엔드는 **그 서버가 하는 일로** 부른다. 위치가 아니라 역할이 이름이 된다:

| 그 서버가 하는 일 | 부르는 이름 |
|---|---|
| LLM 추론 (텍스트 생성·요약·번역) | **LLM 서버** |
| 이미지·영상 생성 (GPU) | **생성 서버** |
| 음성 인식·합성 | **음성 서버** |
| 그 외 | 하는 일을 그대로 (`렌더 서버` 등) |

한 문서 안에서는 **하나로 통일**한다.

거래처 실명도 같은 이유로 뺀다 — 대외 공개 가능성이 있는 문서에서 **누구와 거래하는지**는
서비스 설명에 필요하지 않다(예: 문자 발송 서비스 해설에서 통신사명을 뺀다). 기술 문서와 이어 붙일
필요가 있으면 등장인물 표의 mono 서브라벨에만 남긴다.

 여러 역할이 같은 기계에 있어도 그 문서의 주된 역할로 부른다
(예: 이미지 생성이 주역이고 프롬프트 다듬기에 LLM 도 쓰는 앱이면 `생성 서버` 하나로 간다).

### 말 바꾸기 표

| 쓰지 말 것 | 쓸 것 |
|---|---|
| 특정 기계 이름(사내 서버 호스트명·"사무실 컴퓨터"·기종명) | **역할명 서버** (아래 참조) |
| Worker · 워커 · 엣지 | 클라우드 |
| D1 · 데이터베이스 | 기록 장부 (또는 기록) |
| R2 · 버킷 · 오브젝트 스토리지 | 원본 창고 |
| Queue · 큐 | 대기열 |
| Cron | 정해진 시각에 저절로 (야간 청소부 등 역할 이름) |
| OCR | 글자 인식 |
| JWT · 토큰 검증 | 로그인 확인 |
| fail-closed | 막히는 쪽이 기본 |
| 멱등 | 몇 번 반복해도 안전 |
| 폴백 | 대신 다른 방법으로 넘어감 |
| **거래처·공급사·벤더 실명** (통신사·결제사·CDN·모델 제공사 등) | **역할명** — `통신사`·`결제사`·`콘텐츠 전송망` |

**정확한 이름은 버리지 않는다** — 등장인물 표의 mono 서브라벨과 각주에만 둔다.
기술 문서를 마주쳤을 때 이 해설과 이어 붙일 수 있어야 한다.

### 톤

- 능동태. "처리됩니다" 대신 "처리합니다".
- 그림 캡션은 **주장 한 문장**으로 시작하고 굵게 쓴다. "이 그림은 ~를 보여줍니다" 는 쓰지 않는다.
- 이유를 쓴다. 이 레포의 주석에는 "왜 이렇게 했는가"가 남아 있다 — 그게 이 문서의 가장 좋은 재료다.
- 실패도 쓴다. 실측해서 갈아탄 기록, 일부러 멈추게 만든 곳은 신뢰를 만든다.

### 구성 (기준 사례의 뼈대)

```
표제      — 무엇을 해 주는 서비스인가 + 지대 색 범례
01 여정   — 필수 다이어그램
02~05     — 그 앱의 메커니즘 (STEP 2 에서 고른 것)
06 등장인물 — 이름 / 사는 곳 / 하는 일 표 + 핵심 숫자 카드
07 설계원칙 — "일부러 조용히 넘어가지 않게 만든 것들"
각주      — 근거 파일 + "진실원천과 어긋나면 그쪽이 맞다"
```

07 절은 이 시리즈의 성격이다. 앱마다 **일부러 즉시 실패하게 만든 지점**을 코드 주석에서 찾아 옮긴다.

## STEP 4 — 문서 쓰기

산출물은 두 가지고, **정본은 레포 쪽**이다.

| | 어디에 | 언제 | 그림 |
|---|---|---|---|
| **정본** | `docs/apps/<앱>.md` | **항상** | 머메이드 |
| 게시본 | Artifact (HTML) | 보여 줄 일이 있을 때만 | 손 SVG |

레포를 정본으로 두는 이유: 코드 옆에 있어야 낡은 것이 눈에 띄고, diff 로 리뷰되며,
아티팩트 링크를 따로 관리하지 않아도 된다.

### 4-A. 정본 — `docs/apps/<앱>.md`

> 경로 규약: 기본은 `docs/apps/<앱>.md` 다. 레포가 다른 문서 구조를 쓰면
> `git config aiops.explainDocsDir <경로>` 로 바꾼다(예: `docs/services`·`documentation/apps`).
> **없는 디렉토리를 새로 만들기 전에 그 레포의 문서 관례를 먼저 확인**한다 — 문서 위치는
> 그 레포가 정하는 것이고, 이 스킬이 정할 것이 아니다.

- 문서 머리에 **누구를 위한 문서인지**와 개발자 문서(있으면 `docs/ARCHITECTURE.md` 등) 링크를 둔다.
- 그 다음 줄에 **"진실원천과 어긋나면 그쪽이 맞다"** 를 박는다(레지스트리가 있으면 레지스트리).
- 그림은 머메이드. 문법과 한계는 `reference/diagram-recipes.md` §머메이드 레인.
- 표로 대신할 수 있으면 표로 쓴다 — 머메이드는 나란한 비교에 약하다.
- 맨 끝에 **근거 절**을 둔다(읽은 파일 목록). 값이 바뀌면 거기부터 다시 읽는다.
- `docs/apps/README.md` 색인에 한 줄 추가한다.

### 4-B. 게시본 — Artifact (선택)

손 SVG 라 표현력이 높다. 발표·공유용으로 필요할 때만 만든다.

**`reference/design-system.md` 를 그대로 따른다.** 색은 장식이 아니라
**지대(어디서 도는가)를 인코딩**한다 — 시리즈의 일관성이 여기서 나온다.

- 파일은 스크래치패드에 쓴다. `<!doctype>`·`<html>`·`<head>`·`<body>` 는 쓰지 않는다(게시 시 감싸진다).
- `<title>` 은 넣는다.
- 라이트·다크 **둘 다** 설계한다(토큰 3벌: `@media` + `[data-theme=dark]` + `[data-theme=light]`).
- 외부 폰트·CDN·이미지 금지(CSP 차단). SVG 는 손으로 쓴다.

```
Artifact(file_path=<스크래치패드 경로>, favicon="📄",
         title="<앱> 구조 해설 — <부제>",
         description="<앱> 의 구조를 개발 지식 없이 읽을 수 있게 그림으로 설명한 해설 문서.")
```

- [ ] 그림이 문장보다 빠른가. 아니면 표나 문장으로 바꾼다

### HTML (게시본)

게시 후 **반드시 브라우저로 열어 스크린샷을 본다.** SVG 는 소스가 맞아도 화면에서 깨진다.

- [ ] **SVG 좌측 라벨 잘림.** `text-anchor="end"` 라벨은 viewBox 왼쪽 밖으로 넘어간다.
      `viewBox="-32 0 …"` 처럼 음수 여백을 준다. (기준 사례에서 `Cloudflare Workers` 가 잘렸다)
- [ ] 화살표 라벨이 박스·선과 겹치지 않는가
- [ ] 가로 스크롤이 `.figframe` 안에서만 일어나고 페이지 본문은 안 밀리는가
- [ ] 다크 모드에서 지대 배경 위 글자가 읽히는가
