## 셋 다 관측 방법이었다

판정 로직이 아니라 **그 앞의 관측**이 틀렸다. 실제 URL·실제 데이터로 한 번도 돌려 보지 않으면
드러나지 않는 종류고, 셋 다 zen-koi 의 첫 실사용에서 나왔다.

## #31 방침 점검이 307 을 미게시로 읽었다

app-portal 은 Cloudflare Workers 정적 자산이라 트레일링 슬래시로 307 을 건다.

```
$ curl -s -o /dev/null -w '%{http_code} -> %{redirect_url}' .../zen-koi/privacy
307 -> https://app.devworld.co.kr/zen-koi/privacy/
```

`-L` 이 없어 **게시된 방침에 `HANDOFF_REQUIRED=privacy_policy_not_published` 가 났다.**
app-portal 을 쓰는 모든 앱, 두 스킬 모두 해당이다. `/aiops:app-pages` 가 만든 페이지를
`/aiops:android-release` 가 미게시로 판정하는 모양이었다.

`release:privacy-check` 게이트를 신설했다(android §5-1 · iphone §4-1 공유).

```
307 → 200   통과 — 최종 URL 을 보고에 남긴다
200         통과
404 · 5xx   HANDOFF_REQUIRED
000         검사 불가 — 통과도 실패도 아니다
```

`curl` 이 실패하면 `%{http_code}` 는 `000` 이다. 숫자 비교로만 짜면 "200 이 아니므로 미게시" 로
떨어진다. 최종 URL 과 요청 URL 을 함께 찍어 **엉뚱한 리다이렉트가 200 으로 통과하는 것**도
사람이 볼 수 있게 했다.

## #32 platform_signal=unknown 이 조용히 통과했다

코드가 `// "unknown"` 을 기본값으로 쓰는데 §2 전제 표에 그 행이 없었다. v1.16.1 이전
`/aiops:setup` 이 만든 config 는 이 키가 아예 없다.

#28 에서 두 상태로 나눴지만 실제로는 셋이었다.

```
apps/blog/wrangler.jsonc   신호로 판정
none (fallback)            감지가 돌았고 못 찾음    → 사람이 platform 확인
unknown                    기록 자체가 없음        → /aiops:setup 재실행으로 해소
```

**기능을 추가할 때 이전 산출물이 어떤 값을 갖는지가 빠졌다.** unknown 은 감지 실패가 아니라
기록 부재이고, 자동으로 해소 가능한 상태라 처방이 다르다.

## #33 platforms={} 를 제외로 읽어 릴리즈 노트가 빠졌다

`app-pages` 문서는 `{}` 를 유효하다고 보증하는데 `play_upload` 가 제외로 읽었다.
**app-portal 8개 앱 중 7개가 `{}` 다** — `scanbarcode` 하나만 값이 있다.

`{}` 는 "안 나갔다" 가 아니라 **구분을 적지 않았다**는 뜻이므로 해당으로 읽는다.
`{"android": null}` 은 명시적 제외라 구별한다. 의미를 나중에 좁히면 기존 데이터의 뜻이 바뀐다.

**그리고 누락이 조용했다.** `ℹ️` 한 줄에 종료 코드가 그대로여서 노트 없는 AAB 가 성공으로
업로드됐다. Play 의 "새로운 기능" 이 비어 나가는 것은 업로드가 거부하지 않는다 — 서명 게이트와
달리 **막아 주는 것이 없다.**

```
--no-notes 를 줬다       정상 경로
안 줬는데 못 만들었다     ❌ + 종료 코드 2
```

이유를 다섯으로 나눠 돌려준다 — `no_portal` · `no_file` · `no_releases` ·
`no_android_release` · `unreadable`. 처방이 다르기 때문이다.

곁가지로 §4·§7 예시에 `--portal` 이 없어 **문서대로 따르면 노트가 무조건 빠지던 것**도 고쳤다.
두 겹으로 막혀 있었다.
