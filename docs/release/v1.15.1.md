## ⚠️ platform 판정을 코드가 아니라 산문이 하고 있었다

**§16 이 쓰는 `WEB_DETECTED`·`MOBILE_DETECTED` 가 스킬 어디에서도 계산되지 않았다.**

```bash
# 선행 변수(앵커 밖): WEB_DETECTED(§1~§3·§7), MOBILE_DETECTED(§15) — "true"|"false"
WEB_DETECTED="${WEB_DETECTED:-false}"; MOBILE_DETECTED="${MOBILE_DETECTED:-false}"
```

전수 확인 결과 두 변수는 **앵커 안에서 기본값으로 받기만 한다.** §15 는
`ANDROID_DETECTED`·`IOS_DETECTED`·`RN_DETECTED`·`FLUTTER_DETECTED` 를 만들지만 그것을
`MOBILE_DETECTED` 로 합치는 줄이 없다.

결과적으로 **같은 레포가 실행 주체의 해석에 따라 `web`·`mobile`·`both` 로 갈린다.**
platform 은 `/aiops:mobileflow` 진입 라우팅과 `dev-mobile-*` 분기를 가른다.

## 조치 1 — §15-1 `setup:platform-signals` 신설

두 값을 **파일시스템에서 직접 계산한다.** 앞 절의 산문 결과에 기대지 않는다.

| 값 | 정의 |
|---|---|
| `MOBILE_DETECTED` | 네 플래그의 OR |
| `WEB_DETECTED` | 웹 프레임워크 의존성 **또는** 웹 배포 매니페스트 |

### Gradle·Maven 단독은 웹 신호가 아니다

§1 의 `java` 감지(`build.gradle`·`pom.xml`)를 그대로 웹 신호로 쓰면 **Android 레포가 전부
`both` 가 된다.** Android 도 Gradle 을 쓰기 때문이다.

### `react` 는 단독일 때만 웹 신호다

React Native 는 `react` 를 반드시 의존한다. 같은 `package.json` 에 `react-native` 가 있으면
`react` 를 웹 신호로 세지 않는다. §7 표의 "`react` (단독)" 이 그 뜻이었다.

**첫 구현에서 이 "단독" 을 빠뜨려 RN 레포가 `web=true` 로 잡혔다.** 앵커 없이 부분 문자열을
찾는 v1.11.0 `PASS_DRY_RUN` 과 같은 부류이며, 픽스처가 잡았다.

## 조치 2 — 판정 근거를 남긴다

§16 표의 마지막 행(웹X·모바일X·bin X)은 **안전 기본값이지 판정이 아니다.** 결과만 보면
신호로 `web` 이 된 레포와 구별되지 않아 감지가 제대로 됐는지 알 수 없었다.

```
platform=web  signal=apps/blog/package.json:hono   ← 신호로 판정
platform=web  signal=none (fallback)               ← 기본값. 사람이 봐야 한다
```

폴백이면 경고를 함께 출력한다. **HANDOFF 계약(v1.15.0)의 "확인됨 / 확인했다고 함" 구분과
같은 논리다.**

## 곁가지 — §1 과 §15 의 gradle 매칭 불일치

§1 은 `build.gradle` 만, §15 는 `.kts` 도 봤다. Kotlin DSL 만 쓰는 레포는 `java` 가 누락됐다.
§1 에 `.kts` 를 추가했다.

**이 변경이 platform 판정을 바꾸지는 않는다** — §15-1 에서 Gradle 은 웹 신호가 아니기 때문이다.
`tech_stack` 에 `java` 가 들어갈 뿐이다.

## 역호환

깨지는 변경 없음. `platform=<값>` 형식이 유지되어 기존 소비자의 grep 이 동작한다.
`signal=...` 이 뒤에 붙고, 폴백일 때 경고 한 줄이 추가된다.

**동작이 달라지는 경우가 있다.** 이전에는 실행 주체가 `WEB_DETECTED` 를 해석해 넣었다면 그 값이
쓰였다. 이제는 §15-1 이 계산한 값이 쓰인다. 해석과 계산 결과가 다르면 platform 이 달라질 수 있다 —
**이전 값이 우연히 맞았던 것이고 지금 값이 근거를 가진 것이다.**
