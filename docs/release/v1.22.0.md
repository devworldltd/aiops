### 실패 지점이 나빴다

§5 를 전부 통과하고, 편집 세션을 만들고, **6MB AAB 를 업로드하고**, 트랙까지 반영한 뒤
`edits.commit` 에서 거부된다. **불가역 경계 바로 앞**이다. 커밋 실패라 되돌아가기는 하지만
(zen-koi 실측: 트랙 4개 전부 `[]`, 번들 `(없음)` — `edits.commit` 경계 설계는 정확히 지켜졌다)
로컬에서 끝낼 수 있는 판정을 거기까지 끌고 간다.

**그리고 신규 앱 전부가 걸린다.**

### 보고서의 기준표가 틀렸다

요청서는 "신규 36 / 기존 35" 로 제안했다. 공식 문서는 다르다.

> 2026년 8월 31일부터: **새 앱과 앱 업데이트는** Android 16(API 수준 36) 이상을 타겟팅해야
> Google Play에 제출할 수 있습니다.

**제출 기준은 신규·업데이트가 같다.** 35 는 다른 요건이다 — "앱 제공 가능 요건"(기존 앱이 35
미만이면 최신 OS 기기의 신규 사용자에게 노출되지 않는다)이지 제출을 막는 기준이 아니다.

**그 제안대로 짰으면 35짜리 업데이트를 통과시키고 커밋에서 실패했다** — 고치려던 버그를
업데이트 쪽에 그대로 남기는 셈이다.

폼 팩터마다 다르다(Wear·Automotive 35 · TV·XR 34). 36 을 박아 두면 Wear 앱을 잘못 막으므로
`ANDROID_TARGET_SDK_REQUIRED` 로 조정한다. **요구 수준은 매년 오른다** — 값을 상수로 두고
출처 URL 을 주석에 남겼다.

### 메시지가 오진을 부른다

```
"Target SDK of artifact is too low: 1."
```

`1` 이 versionCode 처럼 보인다 — zen-koi 의 versionCode 가 실제로 1이라 그쪽을 먼저 의심했다.
**실제 값도 요구 값도 메시지에 없다.** 이 게이트는 둘 다 출력한다.

### 빌드 설정이 아니라 AAB 에서 읽는다

`build.gradle.kts` 를 고치고 **다시 빌드하지 않은** 경우를 잡아야 한다 — §5-1 의 "빌드 성공은
서명의 증거가 아니다" 와 같은 논리다.

AAB 의 protobuf manifest 에서 `[field2=이름][field3=값]` 구조만 읽는다. 리소스 참조로 지정돼
숫자가 아니면 **추측하지 않고 종료 코드 2** 다.

```
0  충족        1  미달        2  검사 불가
```
