## §5-1 AAB 서명 게이트 — 빌드 성공은 서명의 증거가 아니다

v1.18.0 의 §5 사전 점검 표는 이렇게 되어 있었다.

```
| AAB 존재·서명 | build/outputs/bundle/release/*.aab | ./gradlew bundleRelease 안내 |
```

한 칸에 두 가지를 묶어 놓고 **실제로는 파일 존재만 봤다.** zen-koi 가 지적했다(2026-09-20).

`build.gradle.kts` 가 `keystore.properties` → 환경변수 순으로 읽고 **둘 다 없으면 서명 없이
빌드되는** 구조가 흔하다(zen-koi·pong 실측). 새 클론이나 CI 의 일반 작업에서도 빌드는 되어야
하므로 일부러 그렇게 둔 것이다. 즉 `bundleRelease` 성공은 서명을 보장하지 않는데, 우리 점검은
그 경우를 **통과시켰다.**

```
0  서명됨          META-INF/*.RSA|DSA|EC 존재
1  서명 없음        사람이 서명 설정을 고쳐야 한다
2  검사 불가        AAB 가 없거나 열리지 않는다 — 처방이 다르다
```

**"AAB 를 열지 못했다" 를 "서명 확인" 으로 판정하지 않는다.** `app-ads` 광고 ID 게이트(v1.14.0),
`merge-main` 조회 실패 차단(v1.14.2), §3-1 왕복 검증(v1.18.1)과 같은 규약이다.

업로드 거부로 드러나므로 불가역 사고는 아니다. 다만 실패가 자격증명 조회·릴리즈 노트·편집
세션 개설을 **다 지나서** 나온다. 앞으로 당겼다.

**어느 키로 서명됐는지는 보지 않는다.** 그것은 Play 업로드가 거부로 알려 주며, 여기서
판정하려면 업로드 키 인증서가 필요하다.

## 업로드 키 2048 → 4096 — 문서가 실제 레포보다 약했다

§3-1(v1.18.1)은 `-keysize 2048` 을 권했다. zen-koi 는 **RSA 4096 / SHA384withRSA** 로 만들어
Play 의 2033-10-22 이후 만료 요건을 넘겼다.

2048 은 관행적 하한일 뿐이다. 이 키는 27년을 쓰고 교체가 수월하지 않으므로 상한을 쓴다.
**스킬이 2048 을 권하는데 실제 레포가 4096 이면, 누군가 문서를 따라 약한 키를 만든다.**

(`duplicate_conflict`) 경로도 단위 테스트에서 `_curl` 을 스텁해 강제로 태웠을 뿐, 실제 KMS 에

미검증으로 남긴다.
